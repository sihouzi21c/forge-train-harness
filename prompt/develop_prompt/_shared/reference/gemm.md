## Stage 1 → Stage 2 baseline state

When entering Stage 2, all GEMM sites have already achieved bitwise alignment in Stage 1 against the active ref stack on the deterministic path (under the torch backend: `ref/reference/train_pure_mup_mtp.py` → `model_pure_mup_mtp.py:TransformerLayer.forward` / `MTPLayer.forward`; under the megatron backend: the equivalent Megatron-LM `ColumnParallelLinear` / `RowParallelLinear` path). Specific characteristics:

**fwd / bwd dgrad / bwd wgrad are treated as the same logical operator**; all three GEMMs must be supported:

```
fwd:        Y = X @ W^T              # 2D GEMM
bwd dgrad:  dX = dY @ W              # 2D GEMM
bwd wgrad:  dW = dY^T @ X            # 2D GEMM (FP32 accumulator)
```

## Hard Constraints

- FP16/BF16 inputs; **use FP32 for the accumulator**
- Disallowed: cuBLAS / `torch::matmul`, scalar FMA, SM80 `mma.sync`
- MFU denominator = 989.4 TFLOPS (H100 SXM dense FP16/BF16 TC peak)

## H100 GEMM technical key points

### Must use SM90 WGMMA + TMA

**Do not start from WMMA/SM80 MMA** — use SM90-exclusive instructions directly:

- **WGMMA (Warp Group MMA)**: throughput is 4-8× that of WMMA
- **TMA (Tensor Memory Accelerator)**: hardware async data movement, zero-overhead global→shared copy

Using CuTeDSL or CUTLASS 3.x `CollectiveBuilder` gives WGMMA + TMA in one step.
**Compilation must specify SM90a**: `-gencode=arch=compute_90a,code=sm_90a`.

### Data layout key points

- **fwd GEMM** (`Y = X @ W^T`): A row-major, B needs col-major stride
- **bwd dgrad** (`dX = dY @ W`): pay attention to the B matrix layout
- **bwd wgrad** (`dW = X^T @ dY`): FP32 accumulation + FP32 output
- Different layouts correspond to different optimal tile configurations; each must be tuned separately

### Known pitfalls (lessons from practice)

1. **CUTLASS 3.x B matrix LayoutTag implicit reversal** — `LayoutTagB = RowMajor` actually corresponds to a ColumnMajor stride.
  Reason: CUTLASS 3.x defines D[m,n] = A[m,k] * B[n,k], with B implicitly transposed inside WGMMA.
2. **R2S copy mapping in the FP32 epilogue** — when outputting FP32 for WGRAD, `CopyUniversalOp` may not correctly handle
  the thread distribution mapping of the WGMMA accumulator, requiring special handling.
3. **3D input reshape** — under the torch backend, training inputs are **[batch, seq, hidden] (BSH)** (**different** from the Megatron baseline's [seq, batch, hidden] (SBH)); the kernel expects 2D, so `reshape(-1, K)`, i.e. `[B*S, H]`, is required.
4. **Remote cutlass-dsl version incompatibility** — the container image may ship with an older version (4.2.1) that is missing some APIs,
  requiring `pip install nvidia-cutlass-dsl==4.4.2` in run_test.sh to upgrade.
5. **ptxas C7510 WGMMA pipeline serialization** — code generated by CollectiveBuilder may trigger this warning;
  persistent kernel or Device LTO can mitigate it.

### Forbidden Anti-Patterns

- **Starting from WMMA/SM80 MMA**: wastes multiple iterations on code that will inevitably be replaced
- **Scalar FMA accumulation**: `fmaf()` / `+=` loops do not go through Tensor Core and are 1000x+ slower than WGMMA
- **Directly wrapping cuBLAS with `torch.matmul` / `torch.addmm`**: that is only the Stage 1 baseline; the goal of Stage 2 is to replace it with an in-house SM90 WGMMA + TMA kernel, not to call a library
- **Ignoring dgrad/wgrad**: fast fwd but unoptimized bwd = training is not accelerated
- **1-producer + N-consumer warp specialization model**: triggers ptxas serialization
- `**wait_group(0)` inside the main loop**: kills the WGMMA pipeline
- **FP16 accumulation**: must use FP32

### NCU verification of Tensor Core usage

```
ncu --metrics smsp__inst_executed_pipe_tensor.sum ./your_kernel
```

A value > 0 indicates Tensor Core is actually being used.

## CuTeDSL Class Interface Contract

The kernel must expose the following interface:

```python
TILE_SHAPE_MN = (128, 128)      # tunable
CLUSTER_SHAPE_MN = (1, 1)        # tunable

# Optional: per-shape configuration dict
SHAPE_CONFIGS: dict = {
    "shape_name": {"tile_mn": (128, 256), "cluster_mn": (2, 1)},
    # Shapes not listed fall back to the TILE_SHAPE_MN / CLUSTER_SHAPE_MN defaults
}

class HopperWgmmaGemmKernel:
    def __init__(self, acc_dtype, tile_shape_mn, cluster_shape_mn): ...

    @cute.jit
    def __call__(self, a: cute.Tensor, b: cute.Tensor, c: cute.Tensor,
                 stream: cuda.CUstream): ...

    @cute.kernel
    def kernel(self, ...): ...  # design the parameters yourself
```

Calling convention:

```python
gemm = HopperWgmmaGemmKernel(acc_dtype, tile_shape_mn, cluster_shape_mn)
compiled_gemm = cute.compile(gemm, mA, mB, mC, stream)
compiled_gemm(mA, mB, mC, stream)
```

Input tensor layouts:

- A: shape (M, K, L), K-major (`mark_layout_dynamic(leading_dim=1)`)
- B: shape (N, K, L), K-major (`mark_layout_dynamic(leading_dim=1)`)
- C: shape (M, N, L), N-major (`mark_layout_dynamic(leading_dim=1)`)

## Detailed milestones for building from scratch (CuTeDSL clean-room practice)

> The following M1-M7 are the detailed technical milestones for building a GEMM kernel from scratch (clean-room implementation scenario).

There are 7 milestones, M1 — M7, **proceeded strictly in order**. Each milestone must be verified PASS before moving on to the next.

### M1 — Single-stage TMA + WGMMA SS (tile=128×128, cluster=(1,1))

**Goal**: build the minimum CuTeDSL kernel that correctly computes GEMM.

**Host side (`__call__`, `@cute.jit`)**:

1. Derive dtype and layout from the input tensors (`a.element_type`, `LayoutEnum.from_tensor(a)`)
2. Create `tiled_mma`: configure the WGMMA instruction
3. Compute `tile_shape_mnk`: the K dimension is determined by the MMA instruction (`mma_inst_shape_k * mma_inst_tile_k`, where `mma_inst_tile_k = 4`, giving BK = 16 × 4 = 64 for FP16)
4. Compute the number of SMEM stages and layout
5. Create TMA atoms (load A, load B, store C)
6. Compute grid size (`ceil(M/BM) × ceil(N/BN) × L`)
7. Define `@cute.struct SharedStorage`: pipeline barriers + A/B SMEM buffers
8. Call `self.kernel(...).launch(grid, block, cluster, stream)`

**Device side (`kernel`, `@cute.kernel`)**:

1. Allocate SMEM (`SmemAllocator().allocate(SharedStorage)`)
2. Create pipeline (`PipelineTmaAsync`)
3. Cluster init sync
4. `local_tile` to split the global tensor into the current CTA's tile
5. Use `tiled_mma.get_slice()` to perform MMA partition
6. Create fragments (`make_fragment_A/B`, `make_rmem_tensor` for the accumulator)
7. Pipeline prefetch: `warp_idx == 0` issues the TMA load
8. Main loop: `consumer_wait → fence → gemm × k_blocks → commit_group → consumer_release`
9. Epilogue: `wait_group(0)` waits for all WGMMA to complete → StMatrix (reg→SMEM) → TMA store (SMEM→GMEM)

**Key technical points**:

- **TMA**: the H100 hardware DMA engine. A tile = (BM, BK) = (128, 64), B tile = (BN, BK) = (128, 64), with the SMEM layout automatically including 128B swizzle
- **WGMMA**: one warpgroup = 128 threads, executes m64×n×k16; SS mode reads A and B from SMEM
- **Origin of BK = 64**: WGMMA k16 instruction × `mma_inst_tile_k = 4` = 64
- **Pipeline**: even a single stage needs mbarriers (`PipelineTmaAsync`); `tx_count` = A tile + B tile SMEM bytes
- **Epilogue**: StMatrix8x8x16b (FP32→FP16→SMEM) + TMA bulk store (SMEM→GMEM); the epi SMEM can share space with the mainloop A SMEM

**Implementation hints**:

```python
tiled_mma = sm90_utils.make_trivial_tiled_mma(
    a_dtype, b_dtype,
    a_layout.sm90_mma_major_mode(), b_layout.sm90_mma_major_mode(),
    acc_dtype, atom_layout_mnk=(1,1,1), tiler_mn=(64, tile_N),
)
mma_inst_shape_k = cute.size(tiled_mma.shape_mnk, mode=[2])
tile_K = mma_inst_shape_k * 4

@cute.struct
class SharedStorage:
    mainloop_pipeline_array_ptr: cute.struct.MemRange[cutlass.Int64, stages * 2]
    sA: cute.struct.Align[cute.struct.MemRange[a_dtype, cute.cosize(a_smem)], 1024]
    sB: cute.struct.Align[cute.struct.MemRange[b_dtype, cute.cosize(b_smem)], 1024]
```

For M1, implementing multi-stage directly (`ab_stage = (smem_cap - 1024) // bytes_per_stage`) is recommended, but the main loop can be simplified to `wait_group(0)` fully serialized.

**Configuration**: `TILE_SHAPE_MN = (128, 128)`, `CLUSTER_SHAPE_MN = (1, 1)`, **expected MFU**: 30-55%

### M2 — Prologue MMA + wait_group overlap

**Goal**: achieve compute/memory overlap between TMA and WGMMA via prologue MMA + `wait_group(k_pipe_mmas)`.

```
Main loop: for k_tile in range(k_pipe_mmas, k_tile_cnt):
  1. consumer_wait(read_state)      ← wait for the current K-tile TMA to complete
  2. fence → gemm × k_blocks → commit_group  ← issue WGMMA
  3. wait_group(k_pipe_mmas)        ← wait for the "round before last" to finish (keep 1 in-flight)
  4. consumer_release(release_state) ← release the old stage's SMEM
  5. if warp_idx==0: producer_acquire → TMA load → producer_commit
```

**Key**: `wait_group(1)` instead of `wait_group(0)` — allows the current round's WGMMA to execute in the background while the next round's TMA is being issued.

**Configuration**: `TILE_SHAPE_MN = (128, 128)`, `CLUSTER_SHAPE_MN = (1, 1)`, **expected MFU**: 50-60%

### M3 — 2-Warpgroup Cooperative + large Tile (tile=128×256)

**Goal**: two warpgroups split the M dimension for WGMMA, paired with a 128×256 tile to improve compute density.

- `atom_layout_mnk = (2, 1, 1)`, 2 warpgroups totaling 256 threads
- Each warpgroup processes half of the M dimension (m64 each), sharing the full N=256 dimension
- `tiler_mn = (64, 256)`, `warp_group_idx = tidx // 128`

```python
warp_group_thread_layout = cute.make_layout(mma_warp_groups, stride=num_threads_per_warp_group)
thr_mma = tiled_mma.get_slice(warp_group_thread_layout(warp_group_idx))
```

**Configuration**: `TILE_SHAPE_MN = (128, 256)`, `CLUSTER_SHAPE_MN = (1, 1)`, **expected MFU**: 65-78%

### M4 — L2 CTA Swizzle (super-tile reordering)

**Goal**: maximize L2 cache hit rate by reordering CTA scheduling.

```python
s_shape = ((group_size_m, cdimx // group_size_m), cdimy)
s_stride = ((1, cdimy * group_size_m), group_size_m)
s_layout = cute.make_layout(s_shape, stride=s_stride)
cid_m, cid_n = s_layout.get_flat_coord(cluster_id % num_reg_cids)
```

Including tail handling: when the number of CTAs along M is not an integer multiple of `group_size_m`, additional tail handling is required.

**Expected MFU**: +2-5% improvement

### M5 — CTA Cluster + TMA Multicast (cluster=(2,1))

**Goal**: reduce HBM bandwidth consumption of the B matrix via TMA multicast within a Cluster.

- B matrix: the 2 CTAs in a cluster share the same B tile → TMA reads it only once and broadcasts it to the 2 CTAs
- Multicast Op: `CopyBulkTensorTileG2SMulticastOp()`, Unicast Op: `CopyBulkTensorTileG2SOp()`
- `mcast_mask` is computed via `cute.make_layout_image_mask(cta_layout_mnk, cluster_coord, mode)`
- The consumer arrive count must be multiplied by mcast_size

```python
# TMA partition must be cluster-aware
a_cta_layout = cute.make_layout(cute.slice_(cta_layout_mnk, (0, None, 0)).shape)
tAsA, tAgA = cute.nvgpu.cpasync.tma_partition(tma_atom_a, a_cta_crd, a_cta_layout, sA_grouped, gA_grouped)
```

**Configuration**: `TILE_SHAPE_MN = (128, 256)`, `CLUSTER_SHAPE_MN = (2, 1)`, **expected MFU**: 78-83%

### M6 — Pipelined Epilogue (StMatrix + TMA Store)

**Goal**: change the epilogue from a naive global write to a register → SMEM → TMA store pipeline.

1. **SMEM reuse**: `sC_ptr = cute.recast_ptr(sA.iterator, epi_smem_layout.inner, dtype=c_dtype)`
2. **StMatrix (R2S)**: `StMatrix8x8x16bOp` converts the FP32 accumulator to FP16 and writes it to SMEM
3. **TMA Store (S2G)**: `warp_idx == 0` issues the TMA bulk store
4. **epi_stage = 4**, epilogue loop:

```
for epi_idx in range_constexpr(epi_tile_num):
    copy acc → rD → type_convert → r2s → sC[epi_buffer]
    fence_proxy(async_shared, shared_cta)
    sync(barrier_id=1)
    if warp_idx == 0: TMA store sC → gC
    c_pipeline.producer_commit() + producer_acquire()
    sync(barrier_id=1)
if warp_idx == 0: c_pipeline.producer_tail()
```

**Expected MFU**: 80-85%+

### M7 — Per-shape optimization (multi-shape configuration tuning)

**Goal**: customize tile/cluster configurations for different GEMM shapes to maximize global MFU.

```python
SHAPE_CONFIGS: dict = {
    "shape_a": {"tile_mn": (128, 128), "cluster_mn": (2, 2)},
    "shape_b": {"tile_mn": (128, 64),  "cluster_mn": (2, 2)},
}
```


| Parameter    | Allowed values                            | Description                                  |
| ------------ | ----------------------------------------- | -------------------------------------------- |
| `tile_mn`    | (128,64), (128,128), (128,192), (128,256) | Smaller tile → more CTAs in parallel; larger tile → more compute reuse |
| `cluster_mn` | (1,1), (2,1), (1,2), (2,2)                | The cluster direction determines whether A or B is multicast |


**Expected MFU**: global mean MFU surpassing cuBLAS (68%)

## Phase 3 — Continuous kernel-level optimization

After M1-M7 are complete, enter Phase 3, where modifying kernel logic (not just configuration) is allowed, but correctness PASS must be maintained for all shapes.

Directions to explore:

1. **Increase occupancy**: `occupancy = 2` (requires halving SMEM → reducing pipeline stages)
2. **Adjust pipeline depth**: smaller tiles can have more stages, which benefits large-K
3. **Tune k_pipe_mmas**: `k_pipe_mmas = 2` keeps more WGMMA groups in flight
4. **Adapt swizzle_group_size_m**: dynamically adjust for small M
5. **SplitK**: split the K dimension across multiple CTAs, a classic optimization for large K and small MN
6. **Epilogue optimization**: streamline the epilogue path for small tiles
7. **Extend SHAPE_CONFIGS**: add fields such as `occupancy`, `k_pipe_mmas`, `stages`
8. **Conditional branching**: use `cutlass.const_expr` to take different kernel code paths for different shape types

### Co-dependency rules

- **M1**: TMA + WGMMA + SMEM + Pipeline + Epilogue must be implemented together — this is the minimum working unit
- **M2**: only changes the main loop structure (prologue + wait_group discipline)
- **M3**: only changes `TILE_SHAPE_MN` + `atom_layout_mnk` auto-switch
- **M4**: only changes CTA coordinate computation in the kernel
- **M5**: only changes `CLUSTER_SHAPE_MN` + multicast logic
- **M6**: only changes the epilogue implementation
- **M7**: only changes the `SHAPE_CONFIGS` configuration
- **Phase 3 kernel optimization**: kernel logic may be changed, but correctness PASS must be maintained for all shapes
